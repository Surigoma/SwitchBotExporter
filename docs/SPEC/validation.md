# 検証・受入条件

Go 版の変更を検証するときは、該当する項目を以下から確認する。実施済みの結果と未確認項目は [検証記録](../records/verification.md) を参照する。

## 検証項目

| 対象 | 確認内容 |
| --- | --- |
| 受信・正規化 | 対象 UUID / Company ID、非対象 ID、異なるアダプター、初期スナップショット、RSSI の有無、履歴値と新着値の区別 |
| デコード | 全型、最小長と 1 バイト不足、未知の種別、余分なバイト、負温度と Fahrenheit、バッテリー、Enum、Contact の拡張時刻、Hub Mini の 40 bit、Curtain 3 の 2 種別 |
| Store | 到着順の両パターン、同一通知、重複、複数 MAC、TTL 境界と上限、正常・不正ペイロードの混在、型変更、RSSI 単独、更新時刻の順序 |
| 互換性 | 同じ入力・固定時刻・名前設定で Python 版と比較し、系列名、型、ラベル、値、Enum の 0/1、時刻、系列数を確認する。小数は誤差を許容し、仕様上の差分は別の期待値で検証する |
| スケジューラ・HTTP・CLI | スキャン失敗と成功への復帰、HTTP の維持、連続スキャンの重複なし、再試行間隔、正常終了、設定・JSON・終了コード |
| 配布・実機 | ELF の CPU・ビット幅と静的リンク、Pi での `version`・`scan`・`/metrics`、systemd、Bluetooth 障害からの復旧、長時間稼働、既存 PromQL |

配布可能な [合成フィクスチャ](../../testdata/advertisements/README.md) と実機採取ログを区別する。実機フィクスチャには機種・信号の種類・取得方法・期待値・匿名化の有無を記録する。実機の MAC や測定ログは共有前に匿名化する。スキャンと BlueZ の結合テストのコマンドは [BLE PoC の検証手順](../guides/ble-poc.md#ビルドとローカルの検証) を参照する。

## 初期リリースの受入条件

以下をすべて満たした時点で初期リリースとする。

- Raspberry Pi Zero W で Go 版が起動し、BlueZ 経由で広告を受信する。
- ARMv6 用の CGO 無効・共有ライブラリ非依存の単一バイナリを生成できる。
- 旧版の対応機種をデコードし、Service / Manufacturer Data の順序差と不正ペイロードを扱えることをテストで確認する。
- 旧版の Prometheus 系列を合成入力で比較し、実機の `/metrics` と `scan` の JSON を確認する。
- [移行手順](../guides/operations.md#切替と切り戻し) を README から参照できる。
- systemd で本番の Go 版への切替、起動、再起動、自動起動設定を確認する。
- BlueZ 再起動とアダプター OFF/ON を実機で試し、自動復旧を確認する。
- 退避した Unit と設定を使った切り戻しを、検証環境で実行して確認する。
- 既存の Grafana と PromQL で表示を確認する。長時間確認の初回は 24 時間を目安に プロセスの常駐メモリ量（RSS）、スキャンの試行回数、取得漏れ、監視値を記録する。

## BLE 受信方式の評価条件

Pi 実機で BlueZ・カーネルの版、アダプター、権限、各採取条件を記録する。BlueZ イベントと同時刻帯の HCI 観測を照合し、MAC、RSSI、両 AD Type、識別子、値の境界、同一データの反復、独立した到着と順序、複数スキャン窓での再受信を評価する。RSSI だけの通知や既存 Device1 に対する通知も確認し、古い辞書値で測定時刻を更新する問題がないか確かめる。Bluetooth サービス再起動、Adapter OFF → ON と再接続中の停止を確認する。捕捉した実機データと合成パケットは由来を明示する。

必要な機種のデータや更新を BlueZ から安定して取得できない場合は、不足した情報と再現条件を記録して Raw HCI を検討する。未確認の項目は [検証チェックリスト](../records/verification.md#初期リリースの確認状況) に残す。
