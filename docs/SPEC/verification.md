# 開発と検証

## 開発時のコマンド

```sh
task test
task lint
go test -race ./...
task build
task build-linux ARCH=amd64
```

`task test` は Go のテスト、`task lint` は `gofmt` と `go vet` を実行する。race detector は対応する開発ホストで実行する。Linux の配布対象とアーカイブ形式は [リリース作業](release.md) を参照する。

CPU の内訳を実機で調べるときは `-tags pprof` でビルドし、環境変数 `SWITCHBOT_PPROF=127.0.0.1:6060` を与えて起動する。`net/http/pprof` がその番地で応答するので、`curl -o cpu.pb.gz 'http://127.0.0.1:6060/debug/pprof/profile?seconds=120'` で採取し、手元の `go tool pprof -top -cum cpu.pb.gz` で読む。タグなしの配布ビルドには含まれない。基準実機での測定例は [ストリーム化の記録](stream.md#負荷の内訳) にある。

## 機種の追加

1. `internal/models/<機種>/` にデコーダーを置き、必要な場合は固有系列の変換も同じディレクトリに置く。[Meter TH の実装](../../internal/models/meterth/) が例になる。
2. [種別表](../../internal/models/registry.go) に機種 ID、名前、必要なペイロード長、デコーダー、公開メトリクスの接頭辞を登録する。
3. [デコード仕様](protocol.md) と [メトリクス表](metrics.md) を更新し、最小長と境界値、互換性をテストする。

## 検証項目

| 対象 | 確認内容 |
| --- | --- |
| 受信・正規化 | 対象 UUID / Company ID、非対象 ID、異なるアダプター、初期スナップショット、RSSI の有無、履歴値と新着値の区別 |
| デコード | 全型、最小長と 1 バイト不足、未知の種別、余分なバイト、負温度と Fahrenheit、バッテリー、Enum、Contact の拡張時刻、Hub Mini の 40 bit、Curtain 3 の 2 種別 |
| Store | 到着順の両パターン、同一通知、重複、複数 MAC、TTL 境界と上限、正常・不正ペイロードの混在、型変更、RSSI 単独、更新時刻の順序 |
| 互換性 | 同じ入力・固定時刻・名前設定で Python 版と比較し、系列名、型、ラベル、値、Enum の 0/1、時刻、系列数を確認する。小数は誤差を許容し、仕様上の差分は別の期待値で検証する |
| スケジューラ・HTTP・CLI | スキャン失敗と成功への復帰、HTTP の維持、連続スキャンの重複なし、再試行間隔、正常終了、設定・JSON・終了コード |
| 配布・実機 | ELF の CPU・ビット幅と静的リンク、Pi での `version`・`scan`・`/metrics`、systemd、Bluetooth 障害からの復旧、長時間稼働、既存 PromQL |

配布可能な [合成フィクスチャ](../../testdata/advertisements/README.md) と実機採取ログを区別する。実機フィクスチャには機種・信号の種類・取得方法・期待値・匿名化の有無を記録する。実機の MAC や測定ログは共有前に匿名化する。スキャンと BlueZ の結合テストのコマンドは [BLE PoC の検証手順](ble-poc.md#ビルドとローカルの検証) を参照する。

## 確認済みの結果

- Raspberry Pi Zero W で BlueZ と HCI の広告フィールド 615 件と RSSI 389 件を照合した。同時採取と未観測の識別子は [PoC 結果](ble-poc.md#判定状況) を参照する。
- Python 版の合成フィクスチャと Go 版のメトリクス 90 系列が一致した。
- Pi で `version` と単発 `scan` を実行し、8 台のデータをデコードした。比較用の一時ポートで 2 回の連続スキャンと機器別の 41 系列を確認し、SIGTERM で正常終了した。
- Pi で存在しないアダプターを指定した場合も HTTP が応答し、エラーカウンターが増えた。検証中、旧 Python サービスは再起動せず稼働を継続した。

### Raspberry Pi Zero W への本番切替

2026-11-28 に `main` のコミット `30cccd0` からビルドした ARMv6 バイナリを配備した。既存の名前表を引き継ぎ、旧 Unit と名前表を `/var/backups/` 以下に退避してから `switchbot-exporter.service` を Go 版に切り替えた。

| 確認時点 | 検出した機器 | 照合した旧系列 |
| --- | ---: | ---: |
| 一時ポートでの事前検証 | 9 台 | 61 / 61 |
| 本番ポートでの起動後 | 9 台 | 61 / 61 |
| systemd での再起動後 | 8 台 | 56 / 56 |

旧版の切替直前 120 秒間に更新された機器は確認できなかったため、同じ MAC を持つ機器の旧スナップショットと Go 版を比較し、系列名とラベルの組が一致した件数を数えた。

再起動後の独立確認では Unit は `active`・`enabled`。ポート 8000 の `/metrics` でスキャン 7 回、エラー 0 件、直近 8 台を確認した。観測中に同じプロセスでスキャン回数と最終成功時刻が更新された。

## 初期リリースの確認項目

以下をすべて満たした時点で初期リリースとする。

- [x] Raspberry Pi Zero W で Go 版が起動し、BlueZ 経由で広告を受信する。
- [x] ARMv6 用の CGO 無効・共有ライブラリ非依存の単一バイナリを生成できる。
- [x] 旧版の対応機種をデコードし、Service / Manufacturer Data の順序差と不正ペイロードを扱えることをテストで確認した。
- [x] 旧版の Prometheus 系列を合成入力で比較し、実機の `/metrics` と `scan` の JSON を確認した。
- [x] [移行手順](operations.md#切替と切り戻し) を README から参照できる。
- [x] systemd で本番の Go 版への切替、起動、再起動、自動起動設定を確認した。
- [ ] BlueZ 再起動とアダプター OFF/ON を実機で試し、自動復旧を確認する。
- [ ] 退避した Unit と設定を使った切り戻しを、検証環境で実行して確認する。
- [ ] 既存の Grafana と PromQL で表示を確認する。長時間確認の初回は 24 時間を目安に RSS、試行回数、取得漏れ、監視値を記録する。

## 移植時の実装順序

1. リポジトリ構成と実装計画を作る。
2. BLE PoC を実装し、Pi 実機の両 AD Type、識別子、RSSI、重複、順序を検証して報告する。
3. PoC を基に受信方式を決める。BlueZ で必要な値が得られない場合は Raw HCI を検討する。
4. デコーダーを移植し、Prometheus Exporter を実装する。
5. 自動テスト、ARMv6 向けビルドを確認する。
6. systemd 対応と移行手順を用意し、旧サービスを退避した状態で切替・切り戻しを検証する。

各段階で実行環境、テスト結果、未解決事項を記録する。推測によるデコードや未観測の電波を実機確認済みとして扱うことを避ける。旧版との差を記録し、最適化は実測に基づける。
